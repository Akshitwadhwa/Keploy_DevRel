# Record a Go URL shortener, then replay it without MySQL

A Go handler that calls MySQL usually leaves you two options: keep a database in CI, or hide the store behind an interface and fake it. Keploy is a third option. You run the real Mux server, send the requests you already use to check the API, and Keploy writes tests from that traffic — including the MySQL conversation. Replay hits the same handlers. The database never has to be there.

<RunMeta />

## The app

[`mux-mysql`](https://github.com/keploy/samples-go/tree/main/mux-mysql) in [keploy/samples-go](https://github.com/keploy/samples-go) is a Gorilla Mux URL shortener on port 8080. This page only uses two routes:

- `POST /create` stores a URL and returns a short link.
- `GET /links/{id}` looks it up and 307-redirects to the original.

`GET /all` exists. It is never called here, so it will not show up in the test set.

There is no Compose file. You start MySQL yourself. The binary will not listen until `ConnectionString` is set.

## Why a Go developer would bother

`httptest` is still the right tool for a pure handler. `_test.go` is still the right place for table-driven logic. This recording is for the path that actually opens a SQL driver: create a row, then follow the redirect.

On record, Keploy sits on the process you pass with `-c`. It keeps each HTTP request and response, and it keeps the queries the driver sent underneath. On replay it plays the HTTP calls back and answers MySQL from those captures. The handler code still runs. The container does not.

That is the useful part. You get a regression check on Mux + MySQL without rewriting the app for mocks, and without leaving MySQL running in CI for this path.

<Callout type="info" title="Watch the binary, not `go run`">

Keploy instruments the command after `-c`. `go run` is a toolchain process that then starts your server. Record `./app` so the interceptor attaches to the process that actually accepts HTTP.

</Callout>

## Setup

You need Docker (MySQL on port 3306), a current Go 1.x toolchain, and the Keploy CLI on your PATH.

Install Keploy from your home directory. The installer writes `install.sh` into the current folder. Doing that inside a repo leaves junk in the project, and later terminals often cannot find `keploy`.

```bash title="terminal"
cd ~
curl --silent -O -L https://keploy.io/install.sh
source install.sh
keploy version
```

Clone the sample and stay in this folder:

```bash title="terminal"
git clone https://github.com/keploy/samples-go.git
cd samples-go/mux-mysql
```

Start MySQL. The app pings the server on boot and creates a `list` table if it is missing. If nothing is listening on 3306, the process exits before HTTP, and Keploy has nothing to save.

```bash title="terminal"
docker run --name mux-mysql \
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \
  -p 3306:3306 \
  -d mysql:8
```

The container can be “up” while MySQL is still initializing. Wait for the ready line:

```bash title="terminal"
until docker logs mux-mysql 2>&1 | grep -q "ready for connections"; do
  sleep 2
done
echo "MySQL is accepting connections"
```

Export the same password and port the container uses. `/mysql` is the built-in schema. The sample does not create another one. Export this in the shell that will build and record. Curl does not need it.

```bash title="terminal"
export ConnectionString='root:my-secret-pw@tcp(localhost:3306)/mysql'
```

Build a single binary. Record and replay must use the same path.

```bash title="terminal"
go build -o app .
```

## Record

Same shell as the export. Leave this running.

```bash title="terminal"
keploy record -c "./app"
```

Wait until it logs that it is listening on `:8080`. Curl before that and you get connection refused. If 8080 is taken, the recording stays empty.

In a second terminal, send exactly two calls. Those two calls are the test set.

`POST /create` stores `https://github.com/keploy/keploy`. On an empty table the id is 1. The handler builds the short link with `localhost`, even if you curl `127.0.0.1`. Same server.

```bash title="terminal"
curl -sS -X POST http://127.0.0.1:8080/create \
  -H 'content-type: application/json' \
  -d '{"link":"https://github.com/keploy/keploy"}'
```

```json title="response"
{"message":"Converted","link":"http://localhost:8080/links/1","status":true}
```

The follow-up is the redirect. `--max-redirs 0` stops curl from chasing GitHub. You want the 307 and `Location: https://github.com/keploy/keploy` — that is the app’s behavior, not GitHub’s HTML.

```bash title="terminal"
curl -sS -D - -o /dev/null --max-redirs 0 http://localhost:8080/links/1
```

Back in the Keploy terminal, Ctrl+C. That stops `./app` and writes `keploy/test-set-1` with `post-create-1.yaml` and `get-links-by-id-1.yaml`.

## Replay with MySQL gone

Stop the container first. A green run while MySQL is still up does not prove the mock.

```bash title="terminal"
docker stop mux-mysql
```

`ConnectionString` is still required. The binary reads it and tries to dial. Keploy intercepts that dial and answers from the recording. A new terminal does not inherit the export.

```bash title="terminal"
export ConnectionString='root:my-secret-pw@tcp(localhost:3306)/mysql'
keploy test -c "./app"
```

You want total tests 2, passed 2, failed 0, and `replay completed successfully`.

<Callout type="warning" title="Read the summary, not the exit code">

`keploy` can exit non-zero after every test has passed. Trust the printed counts and the replay line.

</Callout>

<Callout type="info" title="Leave MySQL stopped">

Replay is supposed to miss the real database. Starting the container again to “help” hides whether Keploy is answering.

</Callout>

## What landed on disk

`keploy/test-set-1` is the recording: HTTP cases plus MySQL mocks.

`post-create-1.yaml` is the POST to `/create` and the `Converted` JSON with `/links/1`. `get-links-by-id-1.yaml` is the GET that must 307 to `https://github.com/keploy/keploy`.

While those two calls ran, the binary created `list` if needed, inserted the URL, then selected it by id. Keploy stored that conversation. On replay it pretends to be MySQL. Change the SQL or the JSON shape and replay fails. That failure is the point. Record again when the new behavior is the one you want to keep.

## If a step fails

<Callout type="warning" title="Three things that empty a recording">

Install Keploy from home so `keploy` is on PATH. Record `./app`, not `go run`. This sample has no Compose file — do not paste a `docker compose` record command from another tutorial.

</Callout>
